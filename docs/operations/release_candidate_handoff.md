# Release candidate handoff

This workflow separates deterministic Linux validation from the manual WeChat
host decision.

## Produce a candidate

```bash
moon info
moon fmt --check
moon test --target native
moon test --target js
bun run check:coverage
bun run check:candidate
git diff --check
```

`check:candidate` first builds release bytes and runs candidate verification,
which always writes `release: false`. It then inspects the recorded Developer
Tools state. A pending candidate stays non-release. If and only if an existing
passed record matches the exact new fingerprint, the repository gate reruns
release verification and restores the committed report to `release: true`.
Malformed or fingerprint-mismatched passed evidence fails closed. The gate does
not publish a package, create a tag, record host evidence, or invent a release
claim.

For one external application, the equivalent command is
`minimoon verify <app> --candidate`. It builds release bytes but deliberately
leaves `release: false` until matching host evidence exists.

GitHub Actions uploads `minimoon-devtools-<commit>` containing:

- the exact `dist/` directory and a convenience zip;
- `SHA256SUMS` plus the zip hash;
- generated manifest, automated verify report, and smoke checklist;
- `HANDOFF.json` with commit, framework artifact fingerprint, import path, and
  required project settings;
- the current manual validation runbook.

`HANDOFF.json` reports one of two evidence states. A matching, passed,
fingerprint-bound record is copied with
`passed-existing-fingerprint-bound-evidence`; a candidate without such a
record uses `pending-manual-devtools-validation` and does not carry stale
evidence into the artifact.

The smoke checklist combines framework-wide host checks with the ordered
application-specific `devtoolsChecks` declared by the fixture configuration.
The reported v2 fingerprint covers the complete distributable tree rather than
only the files named by the manifest, plus the exact manifest and checklist.
Only `project.private.config.json` is excluded as a developer-local override.

## Validate and accept

1. Download the artifact from the exact commit under review.
2. Verify the archive and per-file SHA-256 values.
3. Extract the zip and import its `dist/`; do not rebuild on another machine.
4. Complete `miniapp_devtools_validation.md` in simulator, preview, and physical
   device debugging with a clean console.
5. Record the actual timestamp and Developer Tools version with
   `minimoon devtools record`.
6. Run `minimoon verify ... --release`, then `bun run check:all` followed by
   `bun run check:mvp` from a clean checkout containing that evidence.

If any generated byte, project setting, or source changes after step 1, discard
the result and validate the new artifact. Evidence JSON must never be copied or
edited manually.

## Source-only drift

The current MoonBit release compiler can assign different minified symbols when
MoonBit blocks move between source files. Equal `.mbti` interfaces and passing
tests establish source/API equivalence, but they do not make the generated bytes
identical. The handoff therefore treats any artifact fingerprint change as a
new real-host candidate.
