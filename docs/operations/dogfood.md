# Independent dogfood operation

The offline task-board dogfood application lives in a separate repository so it
cannot accidentally import framework internals or inherit fixture-only files.
Its intended remote is private and operator-owned. Dogfood observations belong
in this repository through the structured issue forms under
`.github/ISSUE_TEMPLATE/`; credentials, private application data, and raw user
content do not.

During unpublished framework development, a local `moon.work` may bind the
dogfood module to a sibling Minimoon checkout. The distributable state removes
that workspace file and resolves the exact registry version instead. No AppID,
Developer Tools private configuration, access token, or package credential is
committed.

## Validation cadence

Run the following automated cycle after every Minimoon change consumed by the
dogfood application:

```bash
bun install --frozen-lockfile
moon info
moon fmt --check
moon check --deny-warn
moon test --target js
minimoon verify . --candidate
```

At least weekly, run a deterministic stress session that repeatedly creates and
mounts pages, dispatches command batches, exercises keyed task state, replaces
subscriptions, and disposes runtimes. Record the iteration count and renderer
work statistics. The run must finish without increasing retained state or
subscription counts after disposal. This is a lifecycle regression check, not
a substitute for long-duration use or physical-device profiling.

For every release candidate, exercise the exact candidate artifacts in all
three host paths:

1. Developer Tools simulator with Skyline and the release configuration.
2. Preview build on a representative physical device.
3. Device debugging for lifecycle, navigation, input, overlay, and failure
   recovery paths affected since the previous candidate.

The canonical nine-route Draft Workbench fixture owns core release evidence; the
independent six-page `ui/examples/showcase` owns UI release evidence. A paired
core/UI release requires both. Dogfood results are application feedback, not
evidence for either fixture, and must never be copied into or used to edit
their evidence JSON manually. Record whether the dogfood consumer resolves
core `0.2.0` alone or the verified core `0.2.0` / UI `0.1.0` pair, including
any development workspace override.

## Observation record

Every API-friction or host-failure report records enough information to compare
runs without exposing application data:

- exact Minimoon version and Git commit;
- generated artifact fingerprint when a build reached verification;
- MoonBit, Node, Bun, Developer Tools, base-library, operating-system, device,
  and renderer environment relevant to the observation;
- renderer work statistics or lifecycle counters when available;
- smallest reproducible application shape and numbered reproduction steps;
- expected and actual behavior;
- whether the problem reproduces in Conformance or the independent UI showcase;
- current workaround and its cost, or an explicit statement that none exists;
- confirmation that AppIDs, credentials, private paths, user data, screenshots,
  logs, and generated snippets were reviewed and redacted before submission.

Use the API-friction form for an awkward, error-prone, or needlessly verbose
supported workflow, even when output is correct. Use the host-failure form for
incorrect generated bytes, lifecycle behavior, routing, rendering, controls, or
Developer Tools/device behavior. Link related reports instead of combining
unrelated observations.

## Feedback review

Review new dogfood reports before planning each release candidate. Classify each
report as documentation, authoring API, runtime/renderer, generator/host,
toolchain, or application-specific. A Minimoon change needs a minimized
regression test at its owning layer; an application-specific report stays
outside the framework backlog. Close a report only after recording the version
or commit that resolves it and rerunning the reproduction at the appropriate
cadence above.

Creating the private remote, granting CI read access to a private Minimoon
source before registry publication, and pushing either repository require an
explicit operator action. The main repository never manufactures credentials or
silently creates that external state.
